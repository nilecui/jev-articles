# 实战赞助邀约：给技术自媒体做一个合作筛选助手

做技术内容之后，邮箱里会逐渐出现不同的合作消息：有人想付费投放开发工具，有人希望互推课程，也有人把产品售后问题发到了合作入口。

如果每封信都从头阅读并套回复模板，工作很重复。但直接让模型决定“接不接广告”，又把商业判断交得太宽。这次我们只做一个小助手：分辨意图和产品类型，为匹配的邀约准备回复草稿。

它来自 `tutorial/` 第 5 章 Level 2 C 的赞助商资格案例，特别适合这个自媒体系列本身。

## 把商业判断收窄为两个分类

假设一封来信是：“我们提供面向开发者的日志检索服务，希望付费赞助下一期技术文章，请发合作资料。”

可以先问两道 Choice：

| 维度 | 选项 | 边界 |
|---|---|---|
| 来信意图 | 付费赞助、售后求助、非付费合作、其他 | “互相推荐”不自动解释为付费 |
| 产品类别 | 开发工具、课程培训、无关产品、信息不足 | 没说清用途时保留 unknown |

这里判断的是来信内容，不是验证公司资质，也不是对产品作质量背书。是否接受合作、报价和内容安排，仍由作者决定。

原仓库 [sponsor-qualification.ts](../apps/ten-levels/src/levels/level02/sponsor-qualification.ts) 包含这两个分类，并在“赞助 + 开发工具”时返回 `autoReply: true`。本文增加置信度检查、`unknown` 出口，并把动作改成草稿建议。

## 输入字段要让问题真正引用到

表单可以包含 `name`、`description`、`opportunity`。其中产品介绍放在 `description`，合作形式可能放在 `opportunity`。

因此，本例的意图问题明确同时引用后两个字段。如果表单已经把“希望付费赞助”放进合作说明，而问题只要求阅读产品介绍，就容易丢掉最关键的证据。

从仓库根目录查看完整请求：

```bash
python3 articles-jev/examples/run_examples.py --request sponsor
```

请求有明确的四类意图与四类产品 criteria，可按第二篇的方法自行提交给官方接口。本次不会发起在线调用；中文效果也需要真实样本验证。

## 四封来信，四条可检查的路径

离线运行：

```bash
python3 articles-jev/examples/run_examples.py sponsor
```

脚本消费的是手写分类与置信度，不是在本地运行 Jev。输出可以按下表理解：

| 场景 | 手写判断 | 输出 |
|---|---|---|
| 开发者日志平台提出付费投放 | sponsorship + dev_tool，两项置信度都高于 0.8 | `draft_media_kit_reply` |
| 同样的产品希望互相推荐 | partnership + dev_tool | `manual_review` |
| 编程课程希望购买推广位置 | sponsorship + course | `manual_review` |
| 提出了赞助，但产品用途不明确 | sponsorship + unknown | `manual_review` |

门槛 0.8 是教学参数。“课程进入人工”也是本文假设的内容定位，并不表示课程不值得合作。若你的账号本来就接受课程推广，可以明确修改规则，再补对应案例。

规则输出只是动作标识，没有发送邮件。匹配时可以在后台生成这样一段固定模板：

> 感谢联系。为了确认合作是否适合本栏目，请补充产品链接、目标受众、期望上线时间及预算范围。收到后我会查看，再沟通具体方案。

这份草稿不承诺档期、报价或接单。作者确认后，才进入自己的正常沟通流程。

## 两项都要检查，不能只看意图

一种常见错误是：模型非常确定对方想付钱，于是系统自动把它当成合适的客户。

但意图明确，不代表产品类别也明确。因此脚本先检查两个分类的置信度，再检查组合关系；任一信息不足，都进入人工队列。`support` 意图则可输出 `support_queue`，把售后消息与商务消息区分开。

如果后续增加品牌匹配、预算区间和排期，建议继续保持职责分明：模型识别文本诉求；数据库查询已有客户状态；金额与日期由代码校验；作者决定是否合作。

不要为了输出一个“综合合作分”把这些步骤全部压进一句问题，否则很难解释一封邮件为什么被排到了前面。

## 让规则可以迭代

第一轮可以只在收件箱旁边增加建议标签，由作者正常处理，再比较差异。重点收集三种边界：没有直接写“付费”但提出预算的来信，既要互推又要购买位置的来信，以及产品名看似技术工具但实际介绍完全不同的来信。

这些样本比反复修改同一封标准邀请更能暴露定义问题。它们也会帮助你发现，哪些决定适合交给分类器，哪些仍然需要阅读上下文。

一个实用的合作筛选助手，首先应该减少重复阅读，同时保留作者对内容和商业合作的判断空间。
