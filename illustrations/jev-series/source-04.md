# 拿到答案以后：用置信度与代码搭起分流系统

模型返回 `billing`，于是程序把工单交给账单团队。这条路径看起来已经完整，但少了一种很常见的情况：模型只是勉强选出了账单团队，对技术团队的可能性也给了不小的权重。

如果程序永远只读最终标签，这两种不同程度的判断就会触发同一个动作。Jev 提供的概率与置信度，让我们有机会把流程设计得更细。

## 先把三个数字分清楚

**概率**对应某个答案。Choice 的 `probabilities` 告诉你每个选项分到多少概率；Noul 则直接用一个数表示回答“是”的概率。

**置信度**是对分布的统计概括。Choice 和 Score 返回 `confidence`；Noul 没有这个字段，可以直接围绕它的概率设置处理区间。[Confidence 官方说明](https://docs.typesafe.ai/confidence)

**准确率**需要带正确标签的数据才能计算。它回答的是“一组真实样本里，有多少判断正确”。因此，看到 `confidence: 0.9`，不能直接写成“这条工单有 90% 的实测正确率”。

还有一个容易漏掉的细节：分到哪个团队的置信度，不能替代挫败感分数的置信度。每个判断需要分别检查，尤其当后者会影响优先级时。

## 给 Noul 留出一个待复核区间

如果问题是“用户是否明确请求退款”，可以先用双阈值展示流程。下面是离线教学函数，阈值仅为演示，不是官方建议值，也没有通过业务评测。

```python
def refund_signal(p):
    if not 0 <= p <= 1:
        raise ValueError("概率必须在 0 到 1 之间")
    if p <= 0.2:
        return "未识别到明确退款诉求"
    if p >= 0.8:
        return "进入退款诉求核查队列"
    return "需要复核诉求"

print(refund_signal(0.2))
print(refund_signal(0.5))
print(refund_signal(0.8))
```

这里的正向分支只进入核查队列。身份、交易、金额和政策检查仍属于后续业务流程。

为什么要把等号写出来？因为阈值是代码，边界值一定会出现。一个解释得通的流程，还需要在实现里明确 `0.2` 和 `0.8` 各走哪条路。

## 四种模式，可以组成一条业务链

官方整理了批量提问、置信度路由、组合评分和意图路由四类模式。本地 [架构模式教程](../tutorial-official/11-架构模式.md) 对应提供了中文解释。[官方 Patterns](https://docs.typesafe.ai/patterns)

把它们放到工单场景里，流程可以这样设计：

1. 对同一份材料，一次询问首接团队、退款诉求、故障影响与表达情绪。
2. 首接分类把握不足，或者选中 `other`，进入人工分诊。
3. 分类足够明确时，交给对应处理器；无关问题的答案不参与该分支。
4. 在相关队列内部，把可靠的评分按业务权重组合，生成排序建议。

这里体现的是四种模式的协作。批量提问减少可以合并的往返，置信度决定是否使用结果，意图决定流向，评分辅助队列内部排序。

批量提问也有边界。如果核查结果必须先从交易系统获取，就不能提前假装知道；如果 state 和问题过长，也要考虑请求预算。一次请求能够做多少，取决于共享材料与数据依赖。

## 排序公式，应该让业务方看得懂

假设我们分别给“功能影响”和“表达情绪”定义三级量表，范围均为 0 到 2。在两项都通过各自的质量检查后，可以采用如下局部计算示意：

```python
# 手写演示值，并非模型输出；两项量表的范围都是 0～2。
impact_score = 1.6
frustration_score = 1.0
priority = 0.8 * (impact_score / 2) + 0.2 * (frustration_score / 2)
print(round(priority, 2))  # 0.74
```

这个公式表达了一个可讨论的业务选择：功能影响权重更高。它没有把 `0.74` 称为“应该优先处理的概率”，因为这只是组合出来的排序值。

如果以后某个量表改成五级，其范围变成 0 到 4，就要同步修改归一化分母。如果某项评分把握不足，应触发复核或按事先验证过的缺失策略处理，不能悄悄当作 0 分。

## 阈值应该从错误成本里长出来

内部错分一张可转派的工单，与错误触发一项外部操作，后果并不相同。即使都用 Choice，也不必共享一个阈值。

选择阈值时，可以同时观察两个量：多少工单进入自动分流，以及自动分流的工单里有多少错分。提高门槛可能减少覆盖率，也可能降低错误率；究竟改善多少，需要实际测量。

再把人工复核能力放进来：如果高峰期积压大量待复核工单，单纯追求模型分支更谨慎，也可能让整体服务变慢。阈值因此是一项业务设计，需要把质量、时延和处理能力放在同一张表里讨论。

一条完整的分流流程还要安排 API 超时、字段异常和服务不可用时的出口。对于这套教学场景，可以回到原有人工队列，并记录原因。模型没有返回答案，不应被当成“没有风险”。

当每条路径都有明确条件和回退方式后，概率才真正成为软件的一部分。下一篇，我们把这种设计带进 Agent 的工具调用流程。
