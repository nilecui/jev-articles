# 实战 Agent：何时压缩上下文，先读哪个文件

Agent 的一次长任务里，有两种成本很容易积累：旧上下文不断保留，新文件不断读入。如果只按固定 token 数压缩，可能在编辑尚未完成时丢掉重要线索；如果每个文件都读进主模型，又可能浪费大量上下文。

`tutorial/` 第 7 章提供了两个具体实验：Level 7 判断压缩时机，Level 8–9 先对文件做局部判断。下面用可运行的策略示例把它们展开。

## 先问工作状态，再看 token 数

Level 7 的 [should-compact.ts](../apps/ten-levels/src/levels/level07/should-compact.ts) 问四件事：任务是否改变、当前工作是否到了边界、下一步需要多少旧历史、是否正处于多步编辑中间。

前三个回答“是否适合整理上下文”，最后一个提供暂停压缩的理由。上下文 token 数则从宿主程序获得，不要求模型估算。

假设 Agent 已结束订单模块排查，用户转而要求编写贡献指南。手写一组演示信号：换任务概率 0.9、编辑中概率 0.1、上下文 16,000 token。策略会返回 `request`。

如果保持其他数据不变，只把“编辑中”改成 0.9，结果就变为 `silent`。因为这时还有部分工作状态需要保留，不能只看到 token 超线就催促压缩。

从仓库根目录运行：

```bash
python3 examples/run_examples.py compact
```

## 边界值决定真实行为

离线案例按原策略的关键顺序实现，使用 6,000、10,000、14,000 三条演示线。只有通过工作状态检查，才根据 token 数分档。

| 输入条件 | 输出 | 原因 |
|---|---|---|
| 换任务明确，16,000 token，非编辑中 | request | 达到请求压缩档 |
| 同样输入，但编辑中概率 0.9 | silent | 编辑中检查先于 token 分档 |
| 换任务明确，恰好 6,000 token | notice | 等于通知线时进入通知档 |
| 换任务概率恰好 0.7，且不满足工作边界条件 | silent | 原代码比较为 `> 0.7` |

这些数字是仓库演示参数，不是官方推荐的通用上下文阈值。离线脚本也不会真的压缩会话，它只是返回建议档位。实际集成还需要宿主程序调用压缩功能，并保存关键结论。

## 第二个案例：先筛选，再读取

假设任务是“查找按比例计费的舍入错误”。我们构造四条文件检查结果：

| 候选路径 | 手写结果 | 应如何处理 |
|---|---|---|
| `src/domain/billing.ts` | 相关概率 0.93 | 保留候选 |
| `tests/billing.test.ts` | 相关概率 0.90 | 保留候选 |
| `docs/style.md` | 相关概率 0.10 | 暂不优先读取 |
| `src/rounding.ts` | 请求超时 | 标记失败，不能判为不相关 |

这些路径仅是案例输入，脚本不会扫描或验证它们实际存在。运行：

```bash
python3 examples/run_examples.py files
```

输出两个候选、一条失败记录，以及“补查失败文件后再选”的建议。保留失败路径很重要：真正的错误可能就藏在那个尚未得到判断的文件里。

## 第二轮选择有真实的数据依赖

原仓库 [ask-files.ts](../apps/ten-levels/src/levels/level09/ask-files.ts) 负责多文件逐个提问；[pick-first.ts](../apps/ten-levels/src/levels/level09/pick-first.ts) 再用 Choice 从候选中选首个读取文件。

这与“同一 state 多问几个问题”不同。第二轮候选依赖第一轮结果，所以需要分阶段。候选键来自程序枚举的路径，另设 `none` 出口。

本例为 Choice 预留一个 `none`，最多接受 254 个文件候选。超过时明确要求分组，而不是静默丢弃后面的文件。原仓库的候选截取和文件剪枝有自己的实现，不能把本文的改进写成原代码已经具备的保障。

实际读取前还要重新检查文件是否存在、是否仍在允许访问的范围，以及内容是否已经变化。模型从有限列表选中一个路径，并不意味着它永久有效。

## 两种机制放在一起，需要观察什么

压缩案例需要观察是否过早丢失历史、是否重复提醒、压缩后是否还能继续原任务。文件筛选需要观察关键文件召回率、漏选后的补查成本，以及总调用量。

如果只是减少了主模型输入，但让 Agent 漏掉关键证据、反复查找，最终收益未必为正。因此“读入更少文件”可以是一项指标，却不能单独证明整个 Agent 更有效。

先把这些建议旁路记录下来，对照 Agent 实际完成任务的过程，才能知道哪些判断值得进入自动流程。
